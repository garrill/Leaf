# CLAUDE.md

Guidance for Claude Code when working in this repo.

## What this is

`Leaf` (formerly `Current`): native SwiftUI macOS git client, 4-column layout (repos → branches/history → changed files → diff). Nearly ready for initial beta release — see "Not yet implemented".

## Build, run, test

No Package.swift — plain Xcode project (`Leaf.xcodeproj`), scheme `Leaf`.

```sh
xcodebuild -project Leaf.xcodeproj -scheme Leaf -configuration Debug build
xcodebuild -project Leaf.xcodeproj -scheme Leaf test
open /path/to/DerivedData/.../Build/Products/Debug/Leaf.app
```

- Quit any running instance before relaunching (`osascript -e 'tell application "Leaf" to quit'`) — xcodebuild won't overwrite a running bundle.
- Don't try to screenshot/screen-record the app (no permission in this terminal) — build, launch, let the user verify visually.
- `LeafTests/LeafTests.swift` has ~50 real unit tests against `GitRepository`, run against throwaway repos in a temp directory (real `git`, no mocks). `LeafUITests/LeafUITests.swift` has a handful of real `XCUIApplication` tests (launch, empty state, Settings window, menu contents); pass `-uiTestReset` (handled in `AppDelegate.resetStateIfRequestedForUITesting()`) to wipe `UserDefaults` first so each test starts from a repo-less sidebar. `LeafUITestsLaunchTests.swift` is still the stock Xcode placeholder.
- App Sandbox is disabled (`ENABLE_APP_SANDBOX = NO`) deliberately — app shells out inside arbitrary repo folders on disk.
- `.swift` files under `Leaf/` are picked up automatically (file-system-synchronized groups) — never need adding to `project.pbxproj`.

## Architecture gotchas

- **Git backend shells out to `/usr/bin/git`**, not libgit2/SwiftGit2 (no SPM package reliably links for macOS arm64).
- **AppState is the single source of truth.** `selectRepo`/`selectBranch` are synchronous on the main thread, re-fetching branches/commits/status directly via git calls. `selectSource`/`selectFile` are assignment-only (plus clearing the now-stale downstream fields — `selectSource` clears `selectedFile`/`diffText`/image data, `selectFile` clears nothing further); the actual changed-files/diff git work happens in `AppState.loadChangedFilesForCurrentSelection`/`loadDiffForCurrentSelection`, called from `ChangedFilesView`/`DiffView`'s own `.task(id:)` off the main thread, debounced ~180ms (skipped on the very first load into an empty list) and automatically cancelled/replaced by SwiftUI if the selection changes again before finishing. `selectRepo` clears `changedFiles`/`selectedFile`/`diffText` synchronously up front so a repo switch never briefly shows the previous repo's files. Callers needing the reload to reflect their own change immediately (`discardChanges`/`ignoreFiles`/`markResolved`) pass `immediate: true` to skip the debounce/detach and run inline. Fetch/pull/push run via `Task { try await Task.detached { ... } }` with explicit `MainActor.run` hops back. A `RepoWatcher` (FSEvents) drives `handleExternalChange()` for auto-refresh on out-of-band changes to the working tree; an `externalChangeGeneration` counter drops a stale in-flight snapshot if a newer FSEvents callback already applied its own.
- **Liquid Glass column header blur** requires `.safeAreaBar(edge: .top)` (not `.safeAreaInset`) paired with `.scrollEdgeEffectStyle(.soft, for: .top)`, and only works over a real SwiftUI `ScrollView`/`List` — never over an `NSScrollView` wrapped in `NSViewRepresentable`. The bar also needs genuine non-empty content (`EmptyView()`/`Text("")` don't render/blur).
- **`.glassEffect(_:in:)` does exist** in the macOS 26.5 SDK (confirmed 2026-08-25 via a real build) — an earlier note here claiming otherwise, based on a `SwiftUI.tbd` symbol grep turning up nothing, was wrong; that grep just wasn't a reliable way to check. `PushSuccessToastView` (`ChangedFilesView.swift`) uses it directly.
- **The window is entirely AppKit-owned, not a SwiftUI `WindowGroup`** (`WindowAccessor.swift` is gone). `LeafApp.swift` declares only a `Settings` scene (Cmd+, Preferences, and to satisfy SwiftUI's "needs a `Scene`" requirement without a stray `WindowGroup`); `AppDelegate` builds a `MainWindowController`, which constructs the `NSWindow` directly (`titled/closable/miniaturizable/resizable/fullSizeContentView`, `window.title = "Leaf"`) and hosts `MainSplitViewController` as its `contentViewController`. This is why: a real `NSSplitViewController` + `NSTrackingSeparatorToolbarItem` is required to pin a toolbar item to an interior column divider, and `NavigationSplitView` can't provide that. `window.setContentSize(...)`/`window.center()` must be re-applied *after* both `contentViewController` and `toolbar` are assigned — assigning them makes AppKit re-derive size from Auto Layout before `MainSplitViewController.viewDidAppear()` has positioned its dividers, silently collapsing the window to the sum of every column's `minimumThickness`.
- **Column layout is `MainSplitViewController: NSSplitViewController`** (`Leaf/Views/MainSplitViewController.swift`), four real `NSSplitViewItem`s (sidebar/branches/files/diff), each hosting its SwiftUI column via its own `NSHostingController` with `sizingOptions = []` (needed so SwiftUI's intrinsic size doesn't fight Auto Layout — the opposite is true for toolbar item hosting views, see below). No `HSplitView`/`NavigationSplitView` anywhere anymore. Initial divider positions can't be set from `minimumThickness` (just a floor) or from a hosting controller's initial frame (not used as a sizing hint) — they're pinned via `splitView.setPosition(_:ofDividerAt:)` from fixed constants in `viewDidAppear()` (has to be after the window is on-screen; `viewDidLayout()` fires too early with stale/zero geometry). Sidebar visibility for the View menu's "Show/Hide Sidebar" is tracked via the `SidebarVisibility` singleton (`ObservableObject`), synced from `NSSplitViewItem.isCollapsed` via KVO, since `LeafApp`'s `.commands` are declared independently of `MainWindowController`/`AppState` and need a way to read AppKit-side split-view state. **Cross-column arrow-key focus navigation is not wired up** — each column is now hosted in its own separate `NSHostingController`, so there's no single shared `@FocusState` across them anymore (see "Not yet implemented").
- **Per-column toolbar items ARE achievable, via AppKit** (the SwiftUI-only approach below was abandoned): `MainToolbarDelegate` (`Leaf/Views/MainToolbarDelegate.swift`) builds the window's `NSToolbar`; the branch-selector menu is pinned to the branches|files divider using an `NSTrackingSeparatorToolbarItem(splitView:dividerIndex:)`, whose x-position AppKit keeps in sync with the live divider as the window/columns resize, with the ordinary `branchMenu` item placed immediately before it riding along (the Mail.app/Notes.app "column-aligned toolbar item" pattern). Gotchas: a toolbar item's custom SwiftUI view, unlike a split-view pane, must keep the *default* `NSHostingView` sizing (no `sizingOptions = []`) or it collapses to near-zero; the branch menu view must avoid `.fixedSize()` and give itself a compressible `minSize`/`maxSize`, or it always claims its full natural width and pops out of the tracking region (detaches from the divider) far earlier than necessary — truncating its text in place instead keeps it pinned at much narrower column widths.
- (Historical/superseded) Earlier attempts at a pure-SwiftUI per-column toolbar (2026-07) hit real dead ends worth remembering if `NSToolbar` is ever abandoned again: toolbar items can't be pinned over a given column — `.navigation` lands at leading, `.principal` centers in the window (a flexible `ToolbarSpacer` drags `.primaryAction` items with it), and items declared on a content column's own `.toolbar` still merge into the window-level trailing group; width-tracked custom items (fixed `.frame` + `.id` to force re-measure) didn't reliably follow column resizes; views layered under the titlebar via `.ignoresSafeArea(.top)` render but never receive clicks (the titlebar/toolbar view swallows them); `.toolbarVisibility(.hidden, for: .windowToolbar)` removes the traffic lights too. The soft scroll edge blur only renders against a column's own `safeAreaBar` — content merely scrolling under the toolbar gets no effect.
- **Commit** (`GitRepository.commit(message:paths:unstagePaths:)`) does `git reset -- <unstagePaths>` (if any), then `git add -- <paths>`, then plain `git commit -m` — pathspec-limited commit fails on untracked files.
- **Diff pane is a real `NSTextView`** (`DiffCodeTextView.swift`), not SwiftUI `Text` rows — needed for real multi-line selection. Built on legacy TextKit 1 explicitly (`makeLegacyTextKit1()`), not the default initializer (can come back TextKit 2-backed with no `.layoutManager`). Gutter is a separate plain `NSView` outside the text view so line numbers never end up in a selection/copy. Added/removed backgrounds are full-row-width, painted manually in `draw(_:)`. Word diff is a simple prefix/suffix trim, not real LCS/Myers.
- **Syntax highlighting** (`HighlightSwift`/highlight.js via JSC) is async and must never block text appearing; results are tagged to the diff text they were computed for so stale highlights can't paint over a newly-selected file. Skipped above ~2000 lines (`DiffView.maxHighlightedLineCount`) to avoid jank.
- **`BranchListView`'s `List(selection:)` uses an `Optional` binding that must ignore `nil` in its setter** — macOS fires a spurious `nil` deselect before every real click; passing it through flashes the diff pane empty. `ChangedFilesView` instead binds `Set<String>` for native multi-select; `AppState.updateFileSelection(_:)` reconciles that against the single file the diff pane shows.
- **Git quotes ambiguous pathnames** (spaces, quotes, non-ASCII) in porcelain/name-status output as C-style escaped strings — always parse through `GitRepository.unquoteGitPath(_:)` or later `checkout`/`clean`/`add` calls silently no-op.
- **Repo icons** (`IconComposerRenderer.swift`) are a hand-rolled approximation of Apple's `.icon` bundle format — there's no public API to rasterize one at runtime. Not pixel-accurate; fine for a sidebar glyph.
- **Sidebar (`SidebarViewController`) is a real `NSOutlineView`**, not a SwiftUI `List` — needed for native drag-reorder with a system-drawn insertion line and "drop on a folder" highlight; a pure-SwiftUI `.draggable`/`.dropDestination` attempt had unfixable dead zones between rows. Row content (`RepoRowView`/`FolderRowView`) is hosted per-cell via `NSHostingView`. Gotchas: don't set `outlineTableColumn` — it reserves native disclosure-triangle space on every row (even level-0) regardless of `indentationPerLevel`; indentation and the expand/collapse chevron are fully custom instead, driven by calling `expandItem`/`collapseItem` directly. `NSHostingView` reuse identifiers must be unique per item id (not shared as one pool key across all folders/repos), or AppKit's view-reuse can hand a row a different item's stale SwiftUI `@State` (rename draft text, focus). A `.onTapGesture` on a row swallows clicks meant for a child `TextField` even if the closure itself checks a condition first — gate it structurally (e.g. only attach via `if` inside `.overlay`) instead. `SidebarViewController` is a plain `NSViewController` owning the `NSScrollView`/`NSOutlineView` directly as its own `view` — **not** an `NSHostingController` wrapping a SwiftUI tree around an `NSViewRepresentable` (which is what it used to be, and is a hard blocker for the titlebar/traffic-light scroll-edge blur below; see that file's doc comment for the reasoning and the full list of things the blur needed together). State sync that used to ride on SwiftUI's `NSViewRepresentable.updateNSView` is now hand-rolled via `withObservationTracking`, re-armed on every fire (`SidebarViewController.observeState()`), the same pattern `MainWindowController.observeTitle()` already used. `renamingFolderID`/`renamingRepoID` live as plain `@Observable` properties directly on `AppState` (no `Binding` plumbing needed since the coordinator reads/writes them straight).
- **Progressive titlebar/traffic-light scroll blur** (`NSSplitViewItemAccessoryViewController.preferredScrollEdgeEffectStyle`, macOS 26.1) only engages for a scroll view that's a direct AppKit view-hierarchy descendant of its split item's own view controller — confirmed by comparison against NetNewsWire's equivalent (code-free) sidebar, and the reason `SidebarViewController` above isn't SwiftUI-hosted. Even with that fixed, the blur needs *every one* of: the outline view's `.sourceList` background left alone (not overridden to `.clear`); `wantsLayer = true` on both the sidebar's root view and the split view (`MainSplitViewController`) — the effect is Core Animation-composited; a real (if auto-hiding) vertical `NSScroller` (`hasVerticalScroller = false` silently disables more than just the visible indicator — the scroll-edge-effect machinery rides the same scroll-position tracking); and a top-aligned `NSSplitViewItemAccessoryViewController` with `preferredScrollEdgeEffectStyle = .soft` on the split item (default is a plain, unblurred pass-through). Any one piece missing and the effect silently no-ops rather than erroring.
- **SwiftUI `.onKeyPress` at an ancestor view fires based on `@FocusState` matching, not on which nested AppKit responder actually has key focus** — worth remembering if/when cross-column arrow-key focus navigation (see "Not yet implemented") gets wired back up: checking `NSApp.keyWindow?.firstResponder is NSTextView` and returning `.ignored` was needed before so editing a hosted rename field wouldn't hijack the keystroke.
- **`TruncationTooltip`'s hidden "ideal width" probe must reuse the modified `content` view itself**, not a fresh `Text(text)` — a fresh one doesn't inherit caller-applied `.font`/`.fontWeight`, throwing off the width comparison and reporting truncation that isn't real.
- **Merge** (`GitRepository.merge(branch:)`) uses `runRaw`, not the throwing `run` — a conflicting merge exits 1 by git's own design, not as a process failure, and exit code alone can't tell that apart from a genuine error (dirty worktree, unrelated histories also exit 1). The reliable discriminator is `.git/MERGE_HEAD` presence after a non-zero exit (`isMergeInProgress()`) — git's own ground truth for "stopped mid-merge." Same file exposes `mergeMessage()` (reads `.git/MERGE_MSG`, prefills the commit box) and `mergeAbort()`.
- **A conflict isn't "resolved" just because the file was hand-edited** — `git status` keeps reporting a path as unmerged (`UU`) until it's staged. `GitRepository.markResolved(_:)` (`git add`) is what actually flips the status; the "Mark Resolved" button in `ChangedFilesView` calls it. Without this step `completeMerge()`'s "any file still `.conflicted`" gate never clears.
- **`FileChangeStatus.conflicted` detection needs the full two-letter porcelain code** (`UU`/`AA`/`DD`/`AU`/`UA`/`DU`/`UD`), checked in `statusEntries()` *before* the normal single-char fallback — some conflict codes (`AA`, `DD`) contain no `U` at all, so they can't be derived from either status char alone.
- **`completeMerge()`'s `git commit` must pass `--cleanup=strip` explicitly** — plain `-m` defaults to `--cleanup=whitespace`, which does *not* strip comment lines, so the `# Conflicts:\n#\tfile` lines from `MERGE_MSG` (prefilled into the commit box) would otherwise get baked verbatim into the real commit message.
- **A conflicted file's raw contents (with `<<<<<<<`/`=======`/`>>>>>>>` markers) aren't unified-diff output** — `DiffView.parse(_:)` requires `@@` hunk headers and silently drops every line until it sees one, so feeding conflict-marker text through it renders as blank. `DiffView.parsePlainText(_:)` is the separate path used instead when `selectedFile?.status == .conflicted`.
- **Stash is single-slot in the UI**: `GitRepository.stashChanges`/`stashList`/`stashCount` wrap plain `git stash push`, but `AppState`/`BranchListView`/`ChangedFilesView` only ever surface `stash@{0}` as a "Stashed Changes" row in the branch/history column — no list of multiple stash entries, no picking which one to view/apply. Switching branches with dirty changes offers stash-and-switch as one of the alert options (`AppState.BranchSwitchDecision`).
- **Sparkle auto-update**: `UpdaterHolder` (`Leaf/UpdaterController.swift`) holds the single `SPUStandardUpdaterController`; `AppDelegate.applicationDidFinishLaunching` touches `UpdaterHolder.shared` once just to force its creation (and `startingUpdater: true`) at launch. `LeafApp`'s "Check for Updates…" command (`CommandGroup(after: .appInfo)`) reaches the same instance through that holder — same reason `AppStateHolder` exists for the Repository menu: SwiftUI's `.commands` are declared independently of `AppDelegate`/`AppState`. Its enabled state comes from `CheckForUpdatesViewModel`, a small `ObservableObject` mirroring `SPUUpdater.canCheckForUpdates` via Combine (Sparkle's own recommended SwiftUI pattern — `SPUUpdater` itself isn't observable). `SUFeedURL` now points at `https://raw.githubusercontent.com/garrill/Leaf/main/appcast.xml` (`appcast.xml`, repo root, tracked in git); it has an empty `<channel>` until a real release exists to point an `<item>` at (see ROADMAP.md #4/#5).
- **Custom Info.plist keys need `INFOPLIST_FILE`, not `INFOPLIST_KEY_*`** — the `Leaf` target has `GENERATE_INFOPLIST_FILE = YES` (no physical Info.plist historically). `INFOPLIST_KEY_<Key>` build settings only synthesize keys from Xcode's own fixed known-key list (confirmed empirically: `INFOPLIST_KEY_LSApplicationCategoryType` works, an arbitrary `INFOPLIST_KEY_MyTestKey` silently gets dropped from the built Info.plist) — Sparkle's `SUPublicEDKey`/`SUFeedURL`/`SUScheduledCheckInterval` aren't on that list. Xcode does support merging a partial plist on top of the generated one: setting `INFOPLIST_FILE` alongside `GENERATE_INFOPLIST_FILE = YES` merges that file's keys in rather than replacing the auto-generated one. `Leaf/Info.plist` (`INFOPLIST_FILE = Leaf/Info.plist` on the `Leaf` target's Debug/Release configs only, not the test targets) holds all three Sparkle keys for this reason. One more gotcha this produced: a loose file dropped into a `PBXFileSystemSynchronizedRootGroup` (see the sidebar/rename note above — same "auto-picked-up" mechanism applies to any file, not just `.swift`) defaults into every build phase including Copy Bundle Resources, so `Leaf/Info.plist` was also getting copied verbatim into `Contents/Resources/Info.plist` alongside the real merged one — silently wrong, and Xcode warns about it. Fixed via a `PBXFileSystemSynchronizedBuildFileExceptionSet` (`membershipExceptions = (Info.plist)`) on the `Leaf` sync group, which excludes it from target membership/build phases entirely; `INFOPLIST_FILE` still finds it fine since that setting resolves a path on disk, independent of target membership.
- **Release scripts/CI**: `scripts/make_dmg.sh` builds Release config to `build/DerivedData` and packages `build/Leaf-<version>.dmg` (plain DMG + `/Applications` symlink, no background image yet, ad-hoc/Development-signed only — Developer ID + notarization steps are commented in the script, blocked on a paid Apple Developer account, see ROADMAP.md #5). `.github/workflows/ci.yml` runs `xcodebuild build` + `xcodebuild test` on `macos-latest` with signing disabled; not yet confirmed green on a real push, and the runner's default Xcode may be older than this project's `objectVersion 77`/macOS 26.5 SDK requirement (see the workflow's own comment).
- **Diff hunks have no header row anymore** — `ec7ba5b` removed the `@@ ... @@` header text in favor of drawing plain borders/gap spacing directly in `DiffCodeTextView` (`HunkSeparatorOverlayView`, gutter/code column vertical borders) to mark hunk boundaries.

## Not yet implemented

Multi-entry stash browsing (apply/drop/view a specific `stash@{n}`, not just the top of the stack). A real 3-way ours/theirs conflict diff view. Promoting `BranchListView` from a commit-history-only view into an actual branch list — branch creation has a dedicated sheet (`NewBranchSheet`) but merging still hangs off `MainToolbarDelegate`'s toolbar branch menu (`BranchMenuToolbarView`). (Branch merging itself — including conflict detection/resolution — is implemented; see `GitRepository.merge`/`mergeAbort`/`completeMerge`/`markResolved`.) Cross-column arrow-key focus navigation — each of the four columns is hosted in its own separate `NSHostingController` since the `MainSplitViewController` AppKit rewrite, so there's no shared `@FocusState` driving focus between them anymore (`DiffView` still takes a `FocusState<MainColumn?>.Binding` parameter, but it's a throwaway local one from `DiffPaneHost`, not connected to the other columns).
